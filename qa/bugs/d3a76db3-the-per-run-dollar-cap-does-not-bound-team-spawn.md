# The PER RUN dollar cap does not bound team.spawn workers, so a 5-cent cap ran 24 cents

## Symptom

SETTINGS › SPENDING LIMITS promises PER RUN is a "Hard ceiling for a single agent run. The run stops the moment it would exceed this." With PER RUN at $0.05, one Commander request that delegates to clones spent $0.24 (lead $0.08 + four workers at $0.04 each), plus $0.08 of post-run aux passes. Each spawned worker carries its own full PER RUN ceiling, and the lead itself finished at $0.08, past its $0.05 cap, reason "done".

## Repro

1. Boot with `SKYNET_BUDGET_PER_RUN=0.05` (or set PER RUN to 0.05).
2. Give the lead the orchestrator object and a model that answers its first turn with `team.spawn` of 4 tasks; every model call costs $0.04 (`usage.cost`).
3. Send one message; read every agent.run.end, the ledger and /api/budget/status.

The PER RUN hint is `frontend/app/stationui.js` "Hard ceiling for a single agent run. The run stops the moment it would exceed this."

## Verdict

Fixed: a run and every worker it starts now share ONE per-run cap. `runOnce` gives each run a spend pool at its own per-run cap (`sidecar/run-spend-pool.js`) and puts it on the host-minted tool ctx. `orchestration.js` passes `ctx.spendPool` into every worker, clone, structured-repair and resumed-worker run, which joins it (a request body can never carry one). The run's budget check asks the pool before each paid call.

How the pool decides (32fc352e4, 8f4267c08). Every call in flight is RESERVED at the most it can cost. `loop.js` prices the call before sending at its prompt (catalog input price) plus the most output it can bill (catalog output price). That output is the lower of two bounds: the model's output ceiling (`provider.outputLimit`, or an output cap a provider named), and the room a window the provider REPORTED for this model leaves. The context manager's cold 131072 guess is never used. With neither bound known, the call has no price. The pool never reserves less than the costliest call any member has booked, and the call settles on what it really booked. A call with no price (a model nothing prices, or one with no reported window and no output ceiling) is counted as a call, and nothing else goes out while it is in flight, so calls that book $0 cannot take the pool around its cap. A call goes out while the family's booked spend is under the cap and either nothing else is in flight or the reservations of the calls in flight leave room. Otherwise it is HELD at its call boundary: it waits until a call in flight settles, then asks again, and a hold ends at once when the run is stopped. A member stops with reason `budget`, scope `run` and the LEAD run's cap only when the family's booked spend has reached the cap, so the COMMS stop line names the cap the Commander set and every stop is a hit. The pool no longer makes projected stops. `loop.js` still puts `budgetProjected: true` on agent.run.end for any check that sets it, and COMMS, channels, ACP and the slag post-mortem keep their "stopped before it would pass the cap" wording for it. A run that never delegates is decided by its loop's own check exactly as before (a one-member pool decides nothing).

The bound. When every reservation covers its call, the family passes the cap by less than the cost of the call admitted last, the same bound the loop gives a single run: that call went out while booked spend plus the reservations beside it were under the cap, and nothing went out after it. The families in the test land inside it, and each one that ends over the cap is OVER it, by less than one call. $0.08 for a $0.05 cap is $0.03 over (the last call cost $0.04). $0.09 for $0.05 is $0.04 over (last call $0.06). $0.65 for $0.50 is $0.15 over (last call $0.20). $1.10 for $1 is $0.10 over (last call $0.30). $1.20 for $1 is $0.20 over: the third $0.30 clone went out with $0.10 left. Heterogeneous clones ($0.02 and $0.20) stay under the cap plus one $0.20 call at every cap tested; on a1234b154 they spent $0.45 under a $0.05 cap. Output-heavy clones on a model with no reported window ($3.30 calls) spend $6.65 for a $5 cap: $1.65 OVER it, less than one call. On 32fc352e4 they spent $9.95, $4.95 over, more than one call.

Limits. A reservation cannot cover a provider that bills a call above the catalog's token prices (once that call books, no later reservation is less), a prompt-cache write premium (up to 1.25x input), a prompt the provider counts above the loop's ruler when the output ceiling (not the window) is the bound, or spend booked outside a model call (a tool's own paid pass, a summarizer fold), which is counted when it is booked. The price of the bound is time. Under a modest cap, a model whose calls must be reserved high makes clones take turns instead of calling at once, and so does a model with no price at all (nothing prices it, or neither a window nor an output ceiling is known: the OpenAI API's /models today). Clones call together only while their reservations fit: three at once at the managed $2 on a 200k-window $3/$15 model with a 64k output ceiling (~$0.97 a call), and all four at $1 on an 8k window at $10/$30 per million. Taking turns does not count against the clocks: `team.spawn`'s timeout and each `team.dispatch` worker's slice pause while a call is held, and still bound each worker's own work. The host's liveness sweep does not count it either: a worker's stall clock stops while its call is held (9e32443bf), and the sweep still stops a worker that is itself silent past its threshold. A foreground `team.resume` worker is not watched; its hold time still counts against its own tool timeout. The input price is cache-blind, so a cached prompt is over-counted. The lead's own between-turn overshoot noted above is the pre-existing single-run bound, unchanged. A flat-subscription lead (no $ cap of its own) bounds the metered crew it starts by PER RUN. Not examined in this fix: the two post-run aux rows the sweep also saw ($0.08 for `agent`) — the regression runs with aux passes off and made no aux call; `BUDGET_PER_WORKER` still lowers a single worker's own ceiling on top of the shared cap.
